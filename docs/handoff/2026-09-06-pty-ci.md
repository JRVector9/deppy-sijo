## 실제 실행 결과

두 PR은 `crates/pty`를 변경하지 않았다. macOS 앱 검사는 각각 2105개와 2107개 통과했고,
그 뒤 PTY 검사 39개 통과 / 1개 실패 / 1개 제외였다. 실패한 검사는 다음 하나다.

`crates/pty/src/lib.rs`의 `고립된_1바이트_echo는_coalesce_대기_전체를_지불하지_않는다`.

| 실행 | PR #147 중앙값 | PR #148 중앙값 | 상한 |

| 최초 CI | 2.034333ms | 2.039208ms | 1.9ms 미만 |
| 실패 job 1회 재시도 | 2.142709ms | 2.143166ms | 1.9ms 미만 |

CI 명령은 `cargo test --workspace --locked -- --test-threads=1`이었다. 따라서 같은 테스트
바이너리 안에서 테스트들이 병렬로 경쟁해서 발생했다고 설명할 수는 없다.

로컬에서는 다음 명령을 실제 실행해 **1 passed**, 0.41초였다.

전체 CI는 실패 상태이며 PR 본문에도 기록했다. 앱 재실행 없이 검사했다.

## 소스 조사와 한계

`PTY_COALESCE_WAIT_MS`는 현재 1이다. 기존 검사는 실제 `/bin/cat` PTY에서 1바이트 echo
10회의 벽시계 왕복 중앙값을 측정한다. writer/reader/자식 프로세스/수신 스레드의 wake
지연과 실제 coalesce poll 대기가 함께 포함되므로 poll에 요청한 예산만 분리해 재는 검사가
아니다. 과거 로컬 측정 1.193ms와 이번 CI 값을 직접 빼서 플랫폼의 고정 오프셋이라고
단정할 수는 없다. 러너 타이머/스케줄링 영향은 후보이며 원인별 계측은 하지 않았다.

두 재시도의 중앙값이 비슷하다는 사실만으로 결정론적 실패라고 단정하지 않는다.
로컬 통과도 CI 실패를 무효화하지 않는다. 실제 CI에서 실패했다는 결과는 유지한다.

## 검토 가능한 후속 수정

Opus/high 읽기전용 담당은 기존 `#[cfg(test)] TestWorkerLiveness` 배선을 따라 실제 reader가
각 배치에 요청한 coalesce timeout 목록을 관측하는 테스트 훅을 제안했다. 실제 고립 echo를
보내고 배치별 누적 대기 요청이 1ms를 넘지 않는지 검사하면, 단순 상수 비교보다 넓게
중복 대기 경로의 회귀를 검증할 수 있다. 실제 지연 측정은 별도 성능 검사로 보존해야 한다.

이 안은 아직 구현·컴파일·검증하지 않았다. 관측 누락으로 검사가 잘못 통과하지 않는지,
기존 2ms 정책과 중복 대기 변형을 실제로 실패시키는지 검토가 필요하다.
이번 UI PR에 검사 상한 완화나 `ignore`를 추가하지 않았다. 제품 PTY 동작도 변경하지 않았다.
