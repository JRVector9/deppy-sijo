워크스페이스 추가

이 Mac 또는 SSH 서버의 폴더에서 작업을 시작합니다.

폴더와 작업은 서버에 유지됩니다.

화면 상태 미리보기

주소만 입력하면 시작됩니다.

기존 SSH 설정의 서버 별칭이나 user@host를 입력합니다. 연결 뒤 같은 화면에서 폴더를 고릅니다.

왼쪽 화면을 직접 클릭하거나 위 상태를 선택해 흐름을 확인할 수 있습니다.

익숙한 추가 화면 유지

내 폴더 · GitHub 저장소 옆에 SSH 서버를 추가합니다. 연결 옵션은 접어 두고, 폴더와 실행 위치를 분명히 표시합니다.

구현 범위

터미널뿐 아니라 파일과 Git도 같은 서버 폴더를 사용해야 합니다. 현재 코드의 재사용 범위와 6개 PR은 검토 탭에 정리했습니다.

서버 폴더를 독립적인 워크스페이스로

서버 주소로 연결하고 폴더를 고르면, 터미널·파일·Git·에이전트가 그 서버에서 동작하는 방식입니다. 로컬 복제나 단순 SSH 셸과 구분합니다.

구현 방식 비교

방식얻는 것제약 · 판단
SSH 셸만 실행가장 작게 시작. 서버 명령 입력 가능.파일트리·Git·에이전트 상태는 로컬 기준으로 남습니다. 이번 요구의 완료로 보기는 어렵습니다.
SSHFS 마운트일부 로컬 파일 API를 재사용할 수 있습니다.별도 설치·마운트 수명·지연 처리가 필요합니다. 터미널과 파일 실행 위치도 따로 맞춰야 합니다.
OpenSSH + 원격 helper 추천서버에서 PTY·파일·Git을 함께 처리. 기존 runtime 프로토콜을 재사용합니다.서버 구성요소 준비와 App runtime 경계 확장이 필요합니다. 사용자 목표에 가장 일관된 방식입니다.

추천 구조

기존 추가 팝업 + SSH 화면
  └─ Local / SSH 워크스페이스 대상
      ├─ 로컬: 기존 runtime · 파일 · Git
      └─ SSH: 연결 워커 → OpenSSH 암호화 채널
                         └─ 서버 helper
                             ├─ PTY · 에이전트 실행 · 상태
                             ├─ 선택한 root의 폴더 · 문서
                             └─ 같은 root의 Git

서버 · 계정 · root · runtime 세대가 모든 응답/입력의 대상 기준입니다.

기존 RemoteRuntimeClient/Server는 재사용 후보이며 SSH 워크스페이스로 완성된 상태는 아닙니다. headless Linux helper의 실제 빌드·의존성 호환과 SSH stdio 전송을 PR 3의 완료 조건으로 둡니다. 세션을 단절 후에도 유지하려면 서버 supervisor/lease가 필요하며 단순 stdio 자식만으로 유지된다고 가정하지 않습니다.

PR 단위 개발 계획

1 → (2 ∥ 3) → 4 → 5 → 6 순서입니다. 2와 3은 1의 계약을 고정한 뒤 병렬로 진행할 수 있습니다. 각 PR은 독립 커밋·회귀 검사를 거치며, 사용자가 실제 기능을 쓰는 시점은 5의 통합 검증 후입니다.

놓치지 않을 동작

상황화면과 기능의 기준
처음 접속하는 서버지문 확인 후 접속합니다. 구성요소 설치는 별도 동의를 받고 사용자 계정 영역에만 수행합니다.
주소 / 계정 변경이전 폴더·응답을 무효화하고 재연결합니다. 이전 서버의 폴더로 추가할 수 없습니다.
네트워크 단절입력 원문을 보존하고 전송 상태를 분리합니다. 재접속만으로 이미 보낸 입력을 다시 보내지 않습니다.
서버 에이전트 미설치지원 상태를 표시하고 원격에서 실행 가능한 에이전트만 선택합니다. 로컬 설치 상태를 사용하지 않습니다.
같은 이름 · 같은 경로서버·계정·원격 root를 포함해 식별합니다. 세션 ID가 같더라도 제목·상태·입력·이력이 섞이지 않습니다.
취소 / 닫기 / 종료연결 취소는 자기 소유 시도만 정리합니다. 워크스페이스 닫기·세션 종료·서버 설정 삭제의 효과를 구분합니다.
