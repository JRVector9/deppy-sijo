# 프로젝트 키 관리 사용법

환경설정의 **환경 및 API → 프로젝트 키**에서 프로젝트와 개발/운영 환경을 선택한다. 같은 이름의 키라도 프로젝트, 환경, 원본별로 따로 관리한다. 기존 에이전트 인증 설정은 **공유·고급 설정**에서 사용할 수 있다.

## 저장·수정·복사

**키 추가**로 이름, 종류, 원본, 사용처를 지정한다. **수정**에서 새 값을 입력하면 새 보관 버전을 만든다. 이미 보관된 키의 새 값 입력을 비워 두면 현재 값을 유지한다. 원본 파일을 선택한 키는 해당 파일의 값도 변경하므로 수정 창의 대상 경로를 확인한다.

값은 목록과 상세에서 숨긴 상태를 유지한다. 숨긴 값 영역을 더블클릭하거나 **복사**를 누르면 현재 프로젝트·환경·보관 버전을 다시 확인한 뒤 클립보드에 복사한다. GitHub에만 있는 키는 원격에서 값을 읽어 복사할 수 없다.

원본과 앱 보관값이 함께 변경돼 충돌하면 **원본 기준** 또는 **보관값 기준**을 명시적으로 선택한다. 누락·빈 원본·보관 실패 상태는 마지막 정상 보관본을 삭제하지 않는다. 상태를 확인하고 원본을 복구하거나 다시 연결한다. 관리 연결 삭제는 원본 파일과 GitHub Secret을 삭제하는 작업이 아니다. 삭제한 파일 키는 감시·새로고침에서 자동으로 다시 등록하지 않으며, 파일 가져오기에서 명시적으로 다시 선택하면 연결을 복구한다.

## 파일 연결과 자동 갱신

**파일 가져오기**에서 환경파일 또는 PEM 파일을 선택하고 필요한 키 이름을 확인한다. **원본 관리**에서 연결 목록과 우선순위를 수정한다. 환경파일은 연결 목록에서 뒤의 파일이 우선한다. 앱 보관 원본으로 직접 입력한 새 키는 명시적으로 우선하는 보관값으로 사용한다.

변경 감시는 설정 화면을 닫아도 동작하며, 재시작과 잠자기 복귀 뒤 연결한 원본을 다시 검사한다. 파일을 연결하지 않았거나 GitHub에만 있는 값은 임의로 찾아 읽지 않는다. 감시를 끄더라도 연결된 빌드 실행 직전에는 원본을 새로 확인한다.

## 최신 키로 빌드

**빌드 설정 추가**에서 빌드 이름, 실행 프로그램, 인수, 프로젝트 안의 실행 경로를 저장한다. **인수 추가**로 각 인수를 별도 입력 칸에 넣는다. 공백·개행이 포함되거나 비어 있는 입력 칸도 하나의 인수이며, 자동으로 셸 문법을 해석하지 않는다. 셸이 필요하면 실행 프로그램과 인수에 직접 명시한다.

앱의 **실행** 또는 아래 CLI를 사용한다. `WORKSPACE_ID`와 `RECIPE_ID`는 화면의 **명령 복사**로 얻는 실제 식별자로 바꾼다.

```sh
deppy-sijo env run --workspace WORKSPACE_ID --environment dev --recipe RECIPE_ID
deppy-sijo env run --workspace WORKSPACE_ID --environment prod --cwd . -- pnpm build
deppy-sijo env run --help
deppy-sijo --version
```

CLI는 GUI 창을 열지 않고 빌드를 실행한다. `--environment`는 `dev`/`development`, `prod`/`production`을 받는다. 실행 경로는 프로젝트 안으로 제한한다. 빌드 직전 필수값과 충돌을 검사하고 한 번의 고정 snapshot을 사용한다. 실행 중 키가 바뀌어도 진행 중인 빌드의 값은 바뀌지 않는다. 사용한 키 이름·버전·시각·종료 결과는 기록하고 비밀 값은 기록하지 않는다. PEM 전달 파일은 제한된 권한으로 만들고 프로세스 종료 후 정리한다.

이 기능은 이미 실행 중인 셸이나 에이전트의 OS 환경을 바꾸지 않는다. 최신값이 필요한 실행은 앱의 연결된 빌드 또는 `env run`을 사용한다.

## GitHub 연결

키 상세의 **GitHub 연결 설정**에서 인증 계정, 인증 토큰 참조, Repository/Environment/Organization 범위, 정확한 Secret 이름을 지정한다. 저장된 토큰 또는 공식 `gh`의 로그인 계정을 사용한다. 개발·운영용으로 보관한 토큰은 해당 환경에서 선택한다.

원격 Secret 이름에는 `GITHUB_` 접두사를 사용할 수 없다. 로컬 `GITHUB_TOKEN` 키를 그대로 보관하고 원격 목적지 이름을 `DEPPY_GITHUB_TOKEN` 등으로 별도 지정한다. [GitHub 이름 규칙](https://docs.github.com/en/actions/reference/security/secrets)에 맞지 않는 목적지는 전송 전에 거절한다.

자동 전송은 명시적으로 켠 경우에만 동작한다. 로컬 보관과 GitHub 전송 상태는 별도로 표시한다. 전송 실패는 보관값을 유지하며 재시도한다. GitHub에서 다른 작업자가 수정한 경우 **외부 변경 · 값 미확인**으로 표시하고 자동 전송을 보류한다. 원격을 덮어쓰려면 화면에서 명시적으로 확인한다.

[GitHub Secrets API](https://docs.github.com/en/rest/actions/secrets)는 원격 Secret의 메타데이터를 제공하며 평문을 반환하지 않는다. 전송은 GitHub 공개키로 원본 바이트를 sealed-box 암호화한 뒤 `gh api` PUT으로 보낸다. 암호문 JSON만 stdin으로 전달하며, 평문과 토큰을 명령 인수나 로그에 넣지 않는다. 줄바꿈도 그대로 보존하고 조직의 선택 저장소는 숫자 ID를 유지한다. 전송 응답이나 사후 메타데이터를 확인하지 못하면 자동 재전송을 멈추고 확인이 필요한 상태를 표시한다. [GitHub App 개인키](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps)는 GitHub에서 다시 다운로드할 수 없으므로 PEM 원본 또는 로컬 보관본을 연결해야 한다.

GitHub의 메타데이터 검사와 Secret PUT 사이에는 원격 원자적 비교 API가 없다. 화면의 전송 완료는 해당 보관 버전의 전송과 사후 메타데이터 확인을 뜻하며 원격 평문이 같음을 읽어 검증한 표시는 아니다. 주기적으로 원격 변경 시각을 확인하고 변경을 감지하면 전송을 보류한다.

검증 결과와 실제 화면 대조는 [수용 검증표](qa/2026-10-12-project-key-management-acceptance.md)에 기록한다.

## 호환성

원격 런타임 wire protocol은 27에서 28로 올린다. 프로젝트 키의 사용처와 제외 이름을 전달하는 필드가 추가되어 이전 peer는 연결 단계에서 버전 불일치로 거절한다. 앱과 원격 런타임을 같은 릴리스로 함께 갱신해야 한다. 새 metadata migration을 연 DB는 이전 앱으로 다시 열지 않는다.
