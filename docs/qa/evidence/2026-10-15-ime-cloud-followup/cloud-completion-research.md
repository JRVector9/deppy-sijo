## Decision for user approval

Recommended smallest honest automatic path: add an opt-in, operation-scoped **deferred MCP tool result over Streamable HTTP SSE, automatically attached to the original submitted input call**. After owner consent for the connection/session, `send_text`/`paste_text` with `submit:true` to a supported known AI execution automatically reserves the watch before sending input. The original RPC stays pending and receives the completion result; **no separate wait tool call is required**. A durable completion receipt supports reconnect without resubmitting input. Existing non-opted-in calls retain their JSON/3-second admission semantics. Opted-in submitted calls explicitly gain deferred-result semantics, advertised in the initialize instructions/tool description and preflight UI.

This requires the cloud host to keep/resume the pending tool request and pass its result to the agent. A transport write only proves bytes were sent; it does not prove the model processed them. Do not promise to wake an arbitrary disconnected cloud agent. If the connector cannot hold/resume an SSE request, show unsupported/disconnected explicitly. Actual Dot, Meta Muse and Grok Bot compatibility is unverified.

Alternative A is MCP Tasks plus task status notifications and result retrieval; better for long work, but experimental and host support is unknown. Alternative B is an explicit provider callback; useful for waking disconnected agents only after a real official callback contract and destination permission exist. Do not add arbitrary callback URLs or reuse inbound OAuth/Bearer credentials for outbound calls in this phase.

## Official protocol / GitHub comparisons

The implementation currently negotiates 2025-03-26, 2025-06-18 and 2025-11-25 (`server.rs:599–600`), so the design should target those pinned contracts. The official SDK main branch also contains newer 2026-era APIs; do not silently mix those into the existing protocol.

| Approach | Interoperability and benefit | Cost / limit | Recommendation |
| --- | --- | --- | --- |
| Original submitted input returns completion over POST SSE | Standard 2025 Streamable HTTP request/response. In opted-in mode, every eligible `send_text`/`paste_text` with submit=true automatically registers a watch and returns the final `CallToolResult` on that very RPC. No second tool or polling loop is needed. | Changes result timing only in explicitly enabled mode. Host timeout, disconnect and final-result handling need testing. A call must remain pending/resumed; this does not wake a host that abandoned the call. | First implementation if user approves; original input→automatic result avoids a wait-tool adoption gap. |
| MCP Tasks + SSE | Dedicated task identity, durable state/results, `tasks/get`, `tasks/result`, optional `notifications/tasks/status`. Fits hours-long work and reconnection. | 2025-11-25 experimental; capability and tool-level negotiation required. Status notification is optional and clients are told to poll as fallback. Receiving it does not mandate running the model. More API/state work. | Follow-up/optional negotiated adapter, not a claim of universal automatic delivery. |
| Explicit provider callback | Can support a documented disconnected-agent wakeup API; delivery can use provider acknowledgment and idempotency. | No such Deppy connector contract has been verified. Adds destination secrets, outbound security and lifecycle. Inbound MCP credential does not authorize outbound provider messaging. | Exclude now; only after named provider/API/destination and owner consent exist. |

Official references inspected:

- [2025-11-25 Streamable HTTP transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports): POST can stream notifications before its final response; GET can open a standalone SSE stream; optional session IDs and Last-Event-ID scope resumption. Send each message on one stream, not every connection. This permits actual server push but does not define model wakeup behavior.
- [2025-11-25 Tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks): task augmentation is negotiated; tools advertise `execution.taskSupport`; status notifications are optional; final results use `tasks/result`. Current Deppy `CloudRun` is not this standard MCP Task and must not be renamed without implementing its protocol.
- [Official TypeScript SDK v1.x streaming server example](https://github.com/modelcontextprotocol/typescript-sdk/blob/v1.x/src/examples/server/simpleStreamableHttp.ts): actual session map and authenticated GET/DELETE, separate active-response tracking, Last-Event-ID handling and idle cleanup. Merely advertising `text/event-stream` cannot replace these parts.
- [Official TypeScript SDK v1.x client example](https://github.com/modelcontextprotocol/typescript-sdk/blob/v1.x/src/examples/client/simpleStreamableHttp.ts): registers notification handlers before connect and preserves transport session identity. A custom notification has no generic guarantee that a host forwards it to its model.
- [Official TypeScript SDK v1.x transport](https://github.com/modelcontextprotocol/typescript-sdk/blob/v1.x/src/server/webStandardStreamableHttp.ts) and [task client](https://github.com/modelcontextprotocol/typescript-sdk/blob/v1.x/src/experimental/tasks/client.ts) provide useful implementation references and an independent synthetic-client interoperability target.

## Exact completion contract

1. Owner explicitly allows completion delivery for a verified connection and exact shared session generation. Reuse read permission as a ceiling but keep opt-in delivery state visible. No callback destination is inferred.
2. Initial supported operation is an explicitly submitted `send_text`/`paste_text` prompt to a known AI execution, with connection/session completion mode already enabled. The watch is automatic and armed atomically before sending input. `submit:false`, Ctrl+C, manual shell text and existing untracked operations are not retroactively assigned a successful task. Default for existing/new connections is off until the owner explicitly enables this permission; after enablement every eligible submission uses it without a per-call wait option.
3. At durable claim, reserve a bounded watch keyed by `(connection_id, run_id, operation_id, session_id, generation)` and capture exact workspace/runtime/pane, AI process identity/birth, native session identity and baseline attention/completion revision. Store no prompt body or token.
4. Arm only when actual PTY admission for that exact operation is accepted. A rejected/unknown admission never becomes completed. Observe a fresh matching TurnStart after the captured baseline and bind its native turn ID/activity episode **plus the exact submitted prompt digest and verified hook execution stamp**. Digest equality alone is never a success witness: the causal ceiling is **accepted original operation → fresh verified TurnStart → same execution/native turn → no intervening input → accepted matching Completed**. Add a monotonic runtime input epoch so any intervening input from keyboard, paste, follow-up, remote or another cloud operation invalidates the watch. This is a new actual-input sequence; existing `Grant.input_epoch` is a permission revision and cannot be reused or interpreted as observed manual input. Serialize tracked submitted work per target until the current turn completes; do not guess between concurrent turns. New tracked submissions during one active watch return a bounded `local_task_busy_no_effect` before any PTY input; idempotent same-operation reconnect/retry resolves the same existing receipt.
5. Completion is matching accepted `Completed` for that bound native turn and original runtime/execution, with no unresolved required response/approval or live child. Expose typed bounded proof from the reducer/storage worker. Do not use local `SessionStatus::Done`, screen silence, progress 100%, badge consumption or cloud `update_run` as the trigger.
6. Existing provider hooks do not all carry native turn IDs or complete prompt payloads. When exact binding cannot be established, return `completion_unavailable`/`unknown`, never claim precise operation completion. Native turn ID absence can use the reducer's unique turn-start revision only when full submitted prompt and exact execution match and there was no intervening input. The existing 256-byte `task_prompt` is a display title and cannot be used as the matching body; `mcp-proxy/main.rs:608–628` shows where the original full UserPromptSubmit prompt and execution stamp are available. Providers without a supported full prompt/start/end hook adapter are unsupported in automatic completion mode. The system has no operation nonce echoed by providers; do not claim causality from a Done transition alone.
7. Once proof is committed, create one durable completion event with a stable event ID and bounded metadata. A DB failure cannot be reported as delivered. Keep cloud agent-reported run state separate from `local_completion` evidence.
8. The original opted-in submitted tool RPC uses a separate deferred reply lane, retains the exact actor/operation/transport session identity and keeps its SSE response pending. Its final standard tool result includes the queue admission receipt separately from `event_id`, `operation_id`, optional `run_id`, exact session/generation, `local_turn_completed`, proof source and observed time. Full terminal output/final answer is excluded by default; use existing separately authorized reads if needed. An optional future read-only completion receipt tool is recovery only, never the claimed automatic-delivery mechanism.

## Delivery, lifecycle and authorization

- Distinguish `armed`, `awaiting_turn`, `working`, `completed_pending_delivery`, `sent`, `acknowledged` (only with an explicit client acknowledgment), `disconnected`, `unsupported`, `expired`, `revoked`, `unknown`. A completed local turn is different from a delivered result. The UI must not display “cloud agent read it” for a socket write.
- Bind streams to verified principal plus random MCP transport/session identity and server/auth epoch. The same connection credential is not enough to broadcast to all hosts. Never let one actor subscribe/read/replay another actor's events, and do not route by active UI tab.
- Deduplicate durable events by exact operation/native turn/completion revision. Network retry is at least once; stable event IDs let clients deduplicate. Never reexecute input when reconnecting/replaying. Final response replay must remain associated with the original request/stream; enforce Last-Event-ID ownership.
- Read-sharing revoke, completion opt-out, connection revoke/expiry, token rotation and stop fence pending sends before bytes are written. Close streams promptly. Already written bytes cannot be recalled. Removing input permission alone need not revoke an already authorized read-only completion receipt, but local-input interruption can make causality unknown.
- Stop/new boot/runtime generation never restores old input, grants or active watches. Persisted facts already completed before stop may remain as local receipts. Unfinished watches become unknown on restart; no stale “success” is sent. Replaying old completed results requires explicitly valid current authorization for the original identity; do not auto-share a new generation.
- Use a bounded queue/off-UI worker, not HTTP writes, DB waits or callback work in egui frames. Separate long-wait capacity from existing ordinary HTTP/call admission. Proposed initial budgets for review: 1 active tracked turn per target, 1 wait stream per watch, at most 16 wait streams globally, 64 active watches, ≤1 KiB status event, 24-hour bounded receipt retention, 15-second heartbeat comment, 60-minute watch expiry. These are design defaults, not existing measured limits.
- Resumption uses authenticated GET for the original stream and Last-Event-ID. Keep a bounded replay ledger by actor/transport/stream. Buffer exhaustion or TTL produces a typed gap/expired result; do not silently drop an event and claim success. Network backoff/jitter and retry deadlines run off UI and never widen destinations.
- Keep routing IDs opaque and unchanged, but redact all display text through current `RedactionService` immediately before send/display. No OAuth/Bearer tokens, credential hashes, environment values, raw prompts, unbounded screens, local filesystem paths or arbitrary tool JSON in events/logs. Bounded error codes only.

### Explicit defaults, deadlines, restart and ACK

- Consent default off; no retroactive watches. After enablement, automatic registration is on for every eligible submit=true operation. Require a known exact native execution, fresh supported hook proof and a free target slot before input. Unknown provider/unsupported adapter returns no-effect if automatic mode is required; turning the setting off restores ordinary admission semantics.
- The local owner is always allowed to type. Do not block their input for the remote watcher. Any non-owned accepted input changes input_epoch, marks the watch `unknown/local_interference`, and sends an honest non-success final response if the original stream is still live. A second tracked cloud prompt while a watch owns the target is rejected before execution, rather than silently queued into another turn.
- Default watch TTL 60 minutes, owner-selectable 5/15/60 minutes; no extension merely because the screen is quiet or a heartbeat was sent. Require matching TurnStart within 30 seconds after accepted submission or finalize `unknown/turn_start_unobserved`. Tool deadlines/admission remain three seconds; this is a distinct completion lifecycle. An idle period does not complete or renew the task.
- SSE sends a comment heartbeat every 15 seconds; it is transport liveness only. A known cloud-host call deadline is respected and its support shown for the chosen TTL. The [official SDK v1.x shared protocol](https://github.com/modelcontextprotocol/typescript-sdk/blob/v1.x/src/shared/protocol.ts#L99) defaults to a 60,000 ms request timeout, `resetTimeoutOnProgress:false`; an explicit `timeout`/`maxTotalTimeout` is needed for supported longer calls. Heartbeat comments are not MCP progress and do not reset that timeout. A 60-minute Deppy TTL cannot override a host's 60-second deadline. If the host times out/closes, retain local proof but set delivery `disconnected`, never `sent` or `acknowledged`.
- Reconnect grace 10 minutes within the watch's 60-minute overall TTL, authenticated original session/stream cursor only; exponential retries with 1/2/4/8/16/30 second caps are client/fixture settings, not a promise a third-party host will retry. When no client is connected Deppy only holds a bounded pending result; no external provider API is called. Expired session returns 404 and records undelivered; fresh initialize does not automatically recover old input consent or reassign a different transport's result.
- Completed event/result retention is 24 hours or a reviewed fixed count cap, whichever comes first. Reserve capacity before submission; do not evict unfinished accepted work to admit another. Current app auth/grants do not survive restart: unfinished watches become unknown on a new boot, completed facts remain local receipts only. Reauthorization of a new generation cannot automatically access the old session's private result.
- `sent` means complete final SSE JSON-RPC response was successfully written/flushed under live authorization. Standard MCP has no final-tool-result acknowledgment. `acknowledged` is available only for a negotiated explicit client ACK keyed by event ID/original operation/session; `Last-Event-ID` proves transport cursor consumption, not that the cloud model read or acted on the result. Never show `agent_processed` without a distinct authenticated semantic confirmation.
