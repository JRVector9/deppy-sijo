# Cloud Agent connection and ended-session review — 2026-09-28

## Measured connection path

The isolated production-path Quick Tunnel measurement returned a generated address at 4.271s, first registered tunnel connection at 4.945s, and verified public MCP metadata at 21.635s. The public verification interval was 17.364s. Earlier isolated samples documented in `docs/CODEX_HANDOFF.md` ranged roughly 11–65s. These are observations on this host and network, not service guarantees. The user screenshot's spinner is shown until `Connection::Ready`; `cloud_agent/tunnel.rs` verifies the public HTTPS resource before advertising the endpoint. Skipping that check would expose an address that may not yet work.

Cloudflare documents that Quick Tunnels generate random temporary hostnames, are intended for development/testing, have no uptime SLA, and may have initial DNS warm-up. Consequently local code can shorten small polling/render overhead, but cannot promise a consistently fast first public URL on Quick Tunnel. A stable named tunnel is an opt-in path for users with a Cloudflare domain; a Deppy-operated relay would support users with no tunnel account or installed tools, but requires operating infrastructure and a separate security design. Sources: [Quick Tunnels](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/), [Tunnel API notes on DNS warm-up](https://developers.cloudflare.com/sandbox/api/tunnels/), [named tunnel setup](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/).

## UI and session history changes

- The public HTTPS `/mcp` URL is the one remote agents need. `127.0.0.1` is the internal loopback listener used by the bundled tunnel and local diagnostics; automatic mode now hides it. Manual mode retains it.
- Current shareable session targets remain exact runtime/pane/generation-bound. The new read-only history loads persisted `sessions.status='exited'` rows, including rows whose panes were closed and removed from `mux_panes`. It excludes duplicate current target rows and never grants MCP read/input access to historical rows.
- History loads on a background read-only SQLite connection and uses virtualized rows. It refreshes while the settings page is open and releases its cache when the page closes. The bounded query supports up to 32,768 rows or 16 MiB; an overflow reports a load error rather than silently claiming a complete list.
- The database open call stays in `app.rs`, the repository's designated composition root. The first full workspace suite caught an initial direct `storage::Db` reference in the Cloud Agent leaf; this was moved behind an injected loader. All 15 `xtask` boundary tests then passed.

## Recommended next PRs

1. **Lossless output retrieval.** Current `read_output` explicitly returns `source=visible_screen`, `lossless=false`, `may_be_stale=true`; intermediate text can disappear between polls. Add a bounded per-session output log with monotonic cursor, explicit gap/reset signals, and redaction before remote delivery. The current snapshot remains useful for full-screen TUIs.
2. **Reliable task completion signal.** `send_text` acknowledges admission into the PTY queue (`completion=not_confirmed`), not command or agent completion. Expose a separate correlated completion/wait state where the local agent/runtime can establish one; never infer success solely from an input receipt.
3. **Stable connection option and clearer stages.** Keep no-install Quick Tunnel as the default, add visible elapsed stages (local listener, URL assigned, tunnel registered, HTTPS verified) and optional named/stable connection for users who configure it. A Deppy-operated relay is the account-free stable endpoint option; evaluate operating costs, revocation, and host authentication before implementation.
4. **Opt-in outbound completion notification.** The existing `notify` tool carries the cloud agent's own final answer into Deppy. The reverse direction still requires the cloud agent to poll `read_output`; an authenticated webhook or client subscription could wake it after a local agent finishes. Cloudflare Quick Tunnels do not support SSE, so any push design must work through a suitable transport or a durable broker. Sources: [Quick Tunnel limitations](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/), [MCP Streamable HTTP transports](https://ts.sdk.modelcontextprotocol.io/server).

Current exact-host/Origin checks, token expiry, explicit session consent and revoke controls should remain part of any transport change. [MCP transport security reference](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

## Stable cloud-agent connectivity research (follow-up)

The user's requirement is a generic hosted agent reaching the MCP server while the Mac and Deppy are running. A public HTTPS address remains necessary for the current remote MCP connector model. Keeping the Mac awake alone does not give a cloud client a route to `127.0.0.1`. If Deppy or its outbound connection stops, live MCP operations stop too; a persistent address alone does not provide offline execution or queued results.

| Method | Address / setup | Fit |
|---|---|---|
| Current bundled Cloudflare Quick Tunnel | No separate install or account; random URL per tunnel process; development/test only, no SLA; no SSE | Low-friction temporary connection, but URL must be re-registered and public readiness has variable delay |
| Cloudflare named Tunnel | Stable custom hostname; user Cloudflare account and domain required | Suitable advanced user option, not the no-account default |
| Tailscale Funnel | Stable public `*.ts.net` HTTPS address; Tailscale installed/account/tailnet configuration required; public client needs no Tailscale | Suitable where the user already has Tailscale |
| ngrok | Account/authtoken and local agent; free account has an assigned development domain with traffic limits and browser interstitial | Possible BYO alternative; confirm the exact hosted MCP client's behavior with the interstitial before recommending free mode |
| Own reverse SSH / direct port and DDNS | Public server or router/port/TLS setup and ongoing maintenance | Advanced self-hosting only |
| Deppy-operated outbound MCP gateway | Stable Deppy-owned HTTPS `/mcp` endpoint; Deppy app holds an authenticated outbound connection to an operated relay; no separate user tunnel/account | Recommended default *after* operating and securing a real gateway; not implemented today |

These product claims are grounded in [Cloudflare Quick Tunnels](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/), [Cloudflare named Tunnel setup](https://developers.cloudflare.com/tunnel/get-started/), [Tailscale Funnel](https://tailscale.com/docs/features/tailscale-funnel), [ngrok pricing](https://ngrok.com/pricing), [ngrok Mac setup](https://ngrok.com/download/mac-os), and [Azure Relay's outbound-only pattern](https://learn.microsoft.com/en-us/azure/azure-relay/relay-what-is-it). The Deppy gateway design is our inference, not an existing external product guarantee.

The repository already has an encrypted WebSocket Relay for browser remote use, but it is **not** an HTTP MCP gateway. `crates/web-remote/src/relay_client/lifecycle.rs` still sets `PRODUCTION_RELAY_ENDPOINT` to `None`; the production route is unassigned. Reusing its deployment, identity and reconnect concepts would help, while the MCP ingress, routing, per-user/device authorization, OAuth/token boundary, rate limits, revocation and audit would require separate design and implementation. Do not relay plaintext MCP inside the existing encrypted browser protocol or describe it as already operational. A small stable routing proxy in front of rotating Quick Tunnels would conceal URL changes but retain Cloudflare Quick Tunnel availability/startup limitations and still require a Deppy-operated HTTPS service; it is an intermediate migration option, not the end state.

Priority: retain Quick Tunnel for immediate account-free fallback, expose existing manually configured stable HTTPS mode for users with named tunnels or equivalent, and plan the outbound Deppy gateway as the ordinary-user path. No alternative was implemented or publicly tested in this research phase.
