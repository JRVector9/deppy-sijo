# 클라우드 에이전트 연결 개선 보고서

작성일: 2026-10-13. 검토 기준: `deppy-sijo-performance`, 커밋 `6bf56f53`, 앱 버전 `0.12.0`.

현재 Deppy는 공유한 Mac 터미널을 클라우드 에이전트가 읽고, 허용된 세션에 입력하고, 답변을 남기는 기능을 갖추고 있다. 앞으로는 **누가 어떤 작업을 맡았는지, 실제로 무엇이 진행됐는지, 결과가 돌아왔는지, 연결이 끊겼을 때 어디서 이어야 하는지**를 관리하는 기능이 필요하다.

## 우선 개선할 부분

### 1. 클라우드 작업과 로컬 터미널 작업을 각각 추적

**확인된 제한:** MCP 도구는 여섯 가지 터미널·답변 기능이다. 클라우드 작업 등록·현재 작업·진행 보고·완료·결과 조회 모델은 없다. `Target.agent_line` 등 로컬 에이전트 정보가 있어도 `list_sessions`는 이를 작업 상태로 내보내지 않는다(`cloud_agent.rs:14`, `:1027`). `notify` 호출은 지시문에 요구하지만 클라우드 에이전트가 실제로 호출해야 결과가 남는다.

**개선:** `connection_id + run_id + session_id + generation`을 기준으로 지시·진행·결과를 묶는다. 클라우드가 보고한 단계와 로컬 터미널에서 관찰한 실행 상태를 별도 필드로 둔다. `queued`, `running`, `needs_input`, `succeeded`, `failed`, `cancel_requested`, `cancelled`, `unknown/stale`의 의미와 전환 근거를 정한다. 큐 접수만으로 실행 중·완료로 바꾸지 않는다. 마지막 보고 시각과 근거 출처를 표시한다.

예: `Grok Bot · 분석 중 · 40초 전 보고`와 `로컬 Codex · 테스트 실행 중`을 함께 표시한다. 보고가 끊기면 오래된 상태임을 알리고 완료로 추정하지 않는다. 외부 봇이 Deppy 밖에서 수행한 작업은 보고나 검증된 제공자 API가 있어야 알 수 있다.

취소도 분리한다. 세션 입력 권한 회수, 로컬 Ctrl+C, 클라우드 작업 취소 요청은 서로 다른 행동이다. 원격 취소 지원 여부와 응답 확인을 보여줘야 한다. 입력을 차단했다고 제공자 내부의 독립 작업까지 중단된 것으로 표시하면 안 된다.

### 2. 연결된 주체별 권한과 입력 제어권

**확인된 제한:** `grants`는 세션 ID별 전역 공유 권한이다(`cloud_agent.rs:31`, `:126`, `:421`). 요청은 scope와 access fingerprint를 검사하지만 승인한 클라이언트 ID를 앱의 권한·이력 판단까지 전달하지 않는다(`server.rs:151`, `oauth.rs:38`). `Record`에도 클라이언트·제공자·작업 ID가 없다(`history.rs:15`).

따라서 승인된 읽기 클라이언트들 사이에서 공유 대상을 다르게 지정하거나, 기록만으로 dot/Muse/Grok Bot 중 누가 입력했는지 구분할 수 없다. 동일 세션에 여러 클라이언트가 접근할 때 하나의 작업이 입력 제어권을 갖는 모델도 없다. 현재 입력 큐와 원자적 paste는 바이트 접수를 보호하지만 서로 다른 작업의 의미상 충돌까지 해결하지 않는다. 이번 조사에서 실제 입력 충돌은 재현하지 않았다.

**개선:** 인증된 연결별 ID, 사용자가 붙인 이름, 허용 프로젝트·세션·행동, 최근 호출, 개별 연결 해제를 관리한다. 동일 세션의 입력 제어권은 한 연결·한 작업이 임시로 보유하고, 사용자는 즉시 회수·인계할 수 있게 한다. 다른 세션의 작업은 계속 독립적으로 진행한다.

OAuth의 `client_name`을 검증된 제공자 신원으로 취급하지 않는다. 제공자가 여러 봇을 하나의 클라이언트로 노출하면 구분 가능한 범위를 `연결 1`·작업 ID로 정직하게 표시하고, 봇별 별도 연결 또는 제공자 측 식별자 지원이 필요한지 확인한다. Bearer도 봇별로 구분하려면 별도 자격 증명 발급·회수가 필요하다.

### 3. 긴 작업에서 읽을 수 있는 출력과 접수 결과

**확인된 제한:** `read_output`은 최대 64 KiB의 현재 화면이다. 응답도 `source=visible_screen`, `lossless=false`, `may_be_stale=true`라고 명시한다(`cloud_agent.rs:1040`). 같은 커서의 `screen=null`은 캐시가 같다는 뜻이다. 출력이 새로 없거나 명령이 끝났다는 증명이 아니다. 숨은 세션의 화면 갱신 요청은 이미 있지만 과거 출력 전체를 읽는 도구는 없다.

**개선:** 기존 터미널 이력 읽기 기능을 재사용해 범위·바이트 수·권한이 제한된 조회를 제공한다. 출력의 관찰 시각, 연속 커서, 누락·잘림 여부, 세션 변경 여부를 명시한다. 구조화된 빌드·테스트 결과를 지원하는 경우 터미널 화면과 별도의 근거로 연결한다.

`tools/call`의 접수 대기는 현재 3초이며, 동시에 처리하는 HTTP 연결은 4개로 제한된다(`server.rs:215`, `:496`). 이 한도 자체를 결함으로 보지 않는다. 다만 접수 응답이 유실됐을 때 읽기 전용 `get_operation`으로 결과를 조회할 수 없고, 혼잡 응답은 공통 재시도 정보가 부족하다.

접수 조회는 입력을 재실행하지 않아야 한다. 결과에 `effect_state`, 오류 코드, 재시도 가능 여부, 다음 조회 시각을 붙인다. 오래 걸리는 작업은 작업 ID로 조회하고, 전체 대기시간이나 스레드 수를 무제한 늘리지 않는다. 여러 봇의 읽기 폴링에는 연결별 예산·공정성을 둔다.

### 4. 재시작·잠자기·만료 후 이어서 사용

**확인된 제한:** 설정에 저장되는 값은 포트·공개 호스트·자동 연결 여부다. 재시작 후 서버와 승인은 꺼진다(`config.rs:187`). 인증도 메모리에 있고 연결은 최대 24시간, OAuth access token은 최대 1시간이다. 정상 중간 refresh는 지원한다. 자동 터널은 짧은 연결 장애 동안 재검사하지만 프로세스 종료·검사 실패 후 연결 종료에는 관리형 재시작 흐름이 없다(`tunnel.rs:290`, `cloud_agent.rs:584`).

Quick Tunnel은 임시 주소이며 호스트가 생성할 때마다 바뀌고, 가동 시간 보장이 없다. 상시 용도에는 고정 호스트를 쓰는 Cloudflare Tunnel 등 기존 수동 연결 경로를 제품에서 쉽게 설정할 수 있어야 한다. [Cloudflare 공식 제한 안내](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)

**개선:** 제공자별 연결 프로필, 주소 방식 선택, 만료 예정 안내, 재인증 버튼, 잠자기 복귀 시 상태 재검증, 제한된 재연결 backoff를 제공한다. 권한 복원은 사용자가 선택한 정책과 확인된 새 세션에 한정한다. 새 generation을 이전 실행과 동일하다고 간주하거나 결과가 불명확한 입력을 자동 재전송하면 안 된다.

Mac이 잠자거나 앱이 종료되면 현재 Mac 터미널 접근은 중단된다. 고정 주소만으로 해결되지 않는다. 계속 작업하려면 별도 실행 호스트 또는 Mac이 깨어 있을 때 UI와 독립적으로 동작하는 bridge가 필요하다.

### 5. 연결 표시와 최초 사용 안내

**확인된 표시 문제:** `cloud.ready = MCP 연결됨`이지만 자동 모드의 Ready는 공개 주소 준비 검사, 수동 모드의 Ready는 로컬 서버 시작으로 결정된다(`cloud_agent/ui.rs:47`, `cloud_agent.rs:628`, `crates/i18n/locales/ko-KR/messages.txt:1398`). 봇의 인증·최근 도구 성공은 확인하지 않는다.

**개선:** `로컬 서버 준비 → 공개 주소 확인 → 클라이언트 인증 → 도구 호출 성공`을 구분한다. 마지막 성공·실패 시각, 실패 단계, 입력 차단 이유를 한 화면에서 확인하게 한다. 연결 확인은 승인된 읽기 전용 검사로 진행하고 실제 터미널에 시험 문장을 입력하지 않는다.

복사 지시문은 `send_text`만 설명하고 `paste_text`를 안내하지 않는다(`cloud_agent/ui.rs:232`). 버튼 이름도 `그록봇 작업 지시문 복사`로 특정 제공자에 묶였다(`messages.txt:1372`). 긴 문장은 UTF-8 바이트 한도와 다중 줄 도구 선택을 안내해야 한다. 설정 기본값은 자동 주소인데 문서의 첫 단계는 수동 공개 호스트 준비다(`docs/cloud-agent-mcp.md:7`). 기본 흐름과 수동 운영 흐름을 따로 설명한다.

### 6. 작업 이력·결과와 모바일

**확인된 제한:** 답변은 세션에 연결되지만 작성 주체·작업 ID·첨부 결과물 정보가 없다(`ui/cloud_answer.rs:3`). 답변 본문은 최근 100개를 보존하며, 일반 작업 이력은 최근 500개와 보존 답변을 제한된 용량으로 읽는다(`history.rs:6`, `:146`). `operation_history_full` 보호 한도는 100,000건이다. 현재 3건이므로 이 한도에 도달한 문제는 아니다.

클라우드 답변 표시 경로는 데스크톱 workspace와 native 알림에 있으며 `crates/web-remote`에는 해당 답변 모델 연결이 없다(`app.rs:27273`, `:27284`, `ui/workspace.rs:7719`).

**개선:** 프로젝트 → 연결 → 작업 단위로 지시·진행·마지막 응답·변경 파일·테스트 결과·PR 링크를 묶는다. 이력 검색·필터·페이지 조회·보존 정책을 제공하고 중복 실행 방지 기록은 일반 답변 보존과 분리한다. PWA도 같은 상태·결과를 읽고 승인·입력 회수·세션 이동을 제공한다. 결과물 링크는 실제 산출물과 검증 여부를 표시한다.

## 제공자별로 확인해야 할 사항

서비스 이름은 OpenAI dot, Meta Muse, Grok Bot으로 해석해 공식 자료를 확인했다. 사용자가 쓰는 서비스가 동명이면 그 서비스의 연결 요구사항을 별도로 대조해야 한다. 공식 제품 설명과 Deppy 실제 연결 완료는 구분한다.

| 제공자 | 공식 자료에서 확인한 범위 | 아직 확인되지 않은 Deppy 연결 항목 |
| --- | --- | --- |
| OpenAI dot | 자체 클라우드 환경에서 앱·작업을 사용하는 에이전트 | 사용자 계정의 임의 MCP 등록·인증 방식·갱신·결과 반환 |
| Meta Muse | 자체 VM·브라우저, 연결 앱과 장기 작업 | 임의 MCP 서버 연결 경로·인증 정책·작업 상태 API |
| Grok Bot | Cursor와 같은 MCP 서버·플러그인·스킬 지원 | Deppy OAuth 승인·refresh·multiline·notify·재연결 실제 흐름 |

근거: [OpenAI dot 공식 안내](https://help.openai.com/en/articles/20001530-getting-started-with-your-dot), [Meta Muse 공식 발표](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/), [Grok Bot 공식 가이드](https://x.ai/bot/guides/grok-bot-101). 앞의 두 자료만으로 임의 Deppy MCP 연결을 보장할 수 없다.

Deppy OAuth는 현재 공개 클라이언트의 동적 등록과 PKCE 경로다. CIMD 및 confidential client 인증 경로는 구현돼 있지 않다(`oauth.rs:183`). MCP 2025-11-25 인증 사양은 CIMD 지원을 권장한다. 실제 제공자의 요구를 확인해 호환성 PR로 추가할 필요가 있는지 판단한다. [MCP 인증 사양](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

현재 MCP는 POST JSON 응답을 사용한다. SSE가 없거나 `GET /mcp`가 405인 사실 자체는 사양 위반이 아니다. 서버의 MCP 세션 ID 발급도 선택 사항이다. 이를 곧바로 연결 결함으로 분류하지 않았다. [MCP 전송 사양](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

MCP Tasks는 실험적 기능이다. 내부 작업 모델을 먼저 구현하고, Tasks를 지원하는 클라이언트와만 협상해 연결한다. Tasks나 SSE를 모든 제공자에게 강제해서 기존 여섯 도구를 깨뜨리지 않는다. Quick Tunnel은 SSE를 지원하지 않으므로 해당 확장에는 연결 방식 대조도 필요하다. [MCP Tasks 사양](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks), [Cloudflare 제한 안내](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)

## 권장 PR 순서와 완료 기준

번호는 제안된 구현 단위다. 이번 조사에서 생성·구현한 PR은 없다. 검증 harness는 PR 1부터 함께 만들고 각 PR마다 실제 동작을 확인한다.

| --- | --- | --- | --- |
| 1 | 서버 준비 표시 수정, 공통 지시문에 paste 안내, 자동·수동 설정 문서 갱신, 실제 제공자 검증표 | 없음 | 인증 전 `봇 연결됨` 미표시; 다중 줄 도구 선택; 읽기 검사로 연결 단계 구분 |

| 3 | 클라우드 작업 등록·진행·결과·로컬 상태 분리·취소 응답 | 2 | `queued`를 완료로 오인하지 않음; 두 작업 상태 독립; 보고 단절은 stale; 취소 요청과 실제 취소 구분 |

PR 4와 5는 PR 2의 주체·권한 계약을 고정한 뒤 병렬 개발할 수 있다. 동일한 인증·작업 모델을 서로 따로 정의하지 않도록 공통 타입 소유자를 정한다. CIMD·MCP Tasks·SSE는 실제 클라이언트 요구와 지원 확인 후 별도 호환성 PR로 다룬다.

첫 업데이트의 체감 목표는 **연결한 봇이 보이고, 그 봇이 맡은 작업이 보이며, 현재 로컬 실행과 최종 결과를 구분할 수 있는 것**이다. 기존 세션·입력의 독립성을 이 과정에서 유지한다.

## 검증 결과와 남은 확인

- 수행: 현재 소스·기존 테스트 코드·설정·이력·답변·PWA 경로 검토, 로컬 수신 포트 확인, SQLite 읽기 전용 집계, 공식 제품·MCP·Cloudflare 문서 대조.
- 미수행: Cargo 테스트, 제공자 계정별 E2E, 실제 입력 충돌·절전 복귀 재현, 구현·재빌드·재실행.
- 기록된 제한들은 코드로 확인했다. 실제 장애 발생률, 어떤 제공자가 세 건의 입력을 보냈는지, 외부 봇 작업의 성공 여부는 현재 증거로 판단할 수 없다.
- 다음 구현 전에 제공자별 정확한 서비스·계정의 연결 화면과 지원 인증 방식을 확인하고, 격리된 세션에서 성공·실패·만료·재시작 증거를 남긴다.
