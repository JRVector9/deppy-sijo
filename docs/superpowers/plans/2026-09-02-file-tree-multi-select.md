# 파일 트리 다중 선택 시안 — 체크박스 방향

> **상태: 시안(제안). 아직 구현하지 않는다.** 아래 「결정이 필요한 것」 6건에 답이 나온
> 뒤에 Task로 내려간다. 구현 착수 시 REQUIRED SUB-SKILL: superpowers:executing-plans.

**Goal:** 파일 트리에서 여러 파일·폴더를 고르고, **고른 것이 무엇인지 화면에 그대로 보이는**
상태로 삭제·복사 같은 일괄 조작을 한다.

**선행:** 2026-09-02 삭제 확인 수정(`DeleteTarget` — 행에서 확정한 값을 확인 문구까지 그대로
들고 간다). 이 시안은 그 규칙을 N개로 확장하는 것이지, 새 규칙을 만드는 게 아니다.

**개정 이력:** 첫 판은 수식키 모델(클릭 = 선택 교체, ⌘클릭 = 토글, ⇧클릭 = 범위)이었다.
2026-09-02 사용자가 체크박스 방향을 지시해 전면 개정했다. 아래 「왜 체크박스인가」가 그
차이를 정리한다. 수식키 판은 이 문서로 대체된다.

## 왜 체크박스인가

**행을 클릭했을 때의 의미가 하나도 바뀌지 않는다.** 이것이 이 방향의 핵심 값이다.

수식키 모델은 "클릭 = 선택 교체"라서 **트리의 모든 클릭 동작을 바꾸는** 변경이었다. 파일
클릭은 지금 아무 일도 하지 않는데 선택을 만들게 되고, 폴더 클릭은 펼침 토글에 선택까지 얹혔다.
체크박스는 선택을 **별도 표적**으로 옮겨 그 위험을 통째로 없앤다 — 폴더 클릭은 여전히 펼침,
파일 클릭은 여전히 무동작, 더블클릭·드래그도 그대로다.

부수 효과 셋:

- **발견 가능하다.** 수식키는 화면에 흔적이 없다. 체크박스는 보인다.
- **접근성이 공짜로 따라온다.** egui 체크박스 위젯을 쓰면 접근성 트리에 `CheckBox` 역할과
  체크 상태가 **저절로** 실린다. 수식키 모델은 라벨에 `selected` 상태를 손으로 실어야 했고,
  그건 관례를 잊으면 조용히 빠지는 종류의 코드였다. 테스트도 Relay 설정이 이미 쓰는
  `get_by_role_and_label(Role::CheckBox, ..)`로 그대로 집힌다.
- **상태가 하나 줄었다.** `anchor`가 사라진다(§1).

대가도 있다. 좁은 사이드바에서 열 하나를 더 쓰고(결정 ①), 폴더 체크박스가 "안의 것도 켜진다"는
인상을 주므로 그 의미를 명시해야 한다(결정 ②·§4).

## 배경 — 지금 트리가 실제로 하는 것

`crates/app/src/ui/file_tree.rs`의 `FileTreeUi`는 **렌더 리프**다. 파일시스템을 읽지 않고
스레드를 만들지 않는다. `FileTreeIoIntent` / `FileTreeMaintenanceIntent`만 내고 App host가
수행한 뒤 정확한 `operation`/`generation`으로 completion을 돌려준다. 다중 선택 설계는 이
경계를 **넘지 않아야** 한다.

지금 있는 것:

- 행 = `FlatRow { path, display_name, depth, is_dir, expanded }`. `flatten`이 펼친 노드를
  평탄화하고 `show_rows`로 가상화한다. 행 Id는 인덱스가 아니라 **경로 기반**
  (`egui::Id::new(("file_tree_row", &row.path))`) — 새로고침으로 목록이 흔들려도 같은 Id가
  다른 파일을 가리키지 않는다. 다중 선택의 안전 근거가 이미 여기 있다.
- 클릭: 폴더 = 펼침 토글, 파일 = (아무 것도 안 함). 더블클릭: 폴더 = 루트 이동, 파일 =
  문서 탭 또는 OS 기본 앱. 우클릭 = 컨텍스트 메뉴. 행 전체가 드래그 소스이며 payload는
  `PathBuf` **하나**다.
- **선택 상태가 없다.** hover 하이라이트만 있고, 포인터가 행을 벗어나면 사라진다.
  그래서 컨텍스트 메뉴가 열려 있는 동안 "지금 어느 행 이야기인가"를 화면이 말해주지 않았다.
- IO 큐 용량은 **1**이다 (`FILE_TREE_IO_QUEUE_CAP = 1`). N개를 지우겠다고 intent를 N개
  던질 수 없다. 대신 `FileTreePathListPayload`가 이미 있고 상한이
  `FILE_TREE_PATH_LIST_MAX_ITEMS = 16` / 256KB다 — `CopyFileUrls`가 쓴다.
- `⌘C`는 **포인터 밑 행**(`hover_row_path`), `⌘V`는 **포인터 밑 대상 폴더**
  (`hover_target_dir`)를 쓴다(`handle_clipboard_shortcuts`).
- 키보드는 트리가 소유하지 않는다. 터미널이 기본 소유자이고, 트리는 "포인터가 트리 영역
  위 + 텍스트에딧 포커스 없음 + 팝업 없음"일 때만 ⌘C/⌘V를 가로챈다.

없는 것: 선택 모델, 선택 표시, 일괄 조작.

## 설계

### 1. 선택 상태 — 두 값

```rust
/// 체크된 경로. 순서는 화면 순서가 아니라 정렬 순서다(일괄 조작 재현성).
checked: BTreeSet<PathBuf>,
/// 키보드 커서. 체크와 별개다 — 체크하지 않고 이동할 수 있다.
/// ⇧+클릭 범위의 기준점 역할도 겸한다(마지막으로 체크를 바꾼 행).
cursor: Option<PathBuf>,
```

수식키 모델이 필요로 하던 `anchor`가 사라졌다 — 체크박스는 그 자체가 토글이라 "교체냐
추가냐"를 기억할 필요가 없다. `edit`/`confirm_delete`와 같은 층에 두고 `set_root`에서
둘 다 지운다(이미 그 자리에 `edit`, `confirm_delete` 초기화가 있다).

### 2. 포인터 규칙 — 기존 동작은 그대로다

| 제스처 | 동작 |
|---|---|
| **체크박스 클릭** | 그 행의 체크를 뒤집는다. cursor = 이 행. **이것이 유일한 포인터 선택 수단** |
| **⇧ + 체크박스** | cursor → 이 행까지 현재 `flat` 순서로 **모두 체크**. 해제하지는 않는다 — 범위 밖 체크를 지우지 않는다 |
| 행 클릭 (폴더) | 펼침 토글 — **지금 그대로** |
| 행 클릭 (파일) | 아무 일도 하지 않는다 — **지금 그대로** |
| 더블클릭 | 그 행 하나만 연다 — **지금 그대로**, 체크와 무관 |
| 드래그 | 잡은 행 하나 — **지금 그대로** |
| 우클릭 | 행이 체크돼 있으면 체크 전체가 대상, 아니면 **그 행 하나만** 대상. **체크는 건드리지 않는다** |

우클릭 규칙이 수식키 판과 다르다. 거기서는 우클릭이 선택을 바꿔치웠지만, 여기서는 체크를
건드리지 않는다 — 체크는 사용자가 명시적으로 만든 것이라 우클릭 한 번에 날아가면 안 된다.
대신 메뉴가 **무엇을 대상으로 하는지**를 항목 문구에 쓴다("체크한 3개를 휴지통으로").

체크박스는 자기 클릭을 삼켜 행 클릭으로 전파하지 않는다 — 그래야 폴더 체크가 펼침을
동시에 토글하지 않는다.

### 3. 키보드

트리가 키를 먹으려면 소유권이 필요하다. **행 클릭·Tab으로 트리 스크롤 영역에 포커스를 주고,
`ui.memory(|m| m.has_focus(tree_id))`일 때만** 아래 키를 처리한다. 포인터 위치 게이트
(⌘C/⌘V가 쓰는 것)는 쓰지 않는다 — 마우스를 얹어놓기만 해도 방향키가 터미널에서 샌다.

| 키 | 동작 |
|---|---|
| ↑ / ↓ | cursor를 `flat` 위아래로. **체크는 건드리지 않는다** (수식키 판과 다른 점 — 거기선 선택이 따라 움직였다) |
| Space | cursor 행의 체크를 뒤집는다 — 체크박스 클릭의 키보드판 |
| ⇧+↑ / ⇧+↓ | 이동하면서 지나는 행을 체크 |
| ← / → | 폴더면 접기/펼치기(기존 `toggle_dir`), 파일이면 부모로 / 무시 |
| ⌘A | 요약 줄의 전체 체크박스와 같다 — **보이는 행 전부**(`flat`. 접힌 폴더 안·숨김 필터로 걸러진 행은 안 들어간다) |
| Esc | 체크 해제 + 열려 있는 영구삭제 확인 닫기 + 트리 포커스 반납 |
| Enter | cursor 행 열기(더블클릭과 같은 길) |
| Delete / ⌫ | **바인딩하지 않는다** (아래 「하지 않는 것」) |

### 4. 폴더 체크는 무엇을 뜻하나

체크박스를 달면 곧바로 생기는 질문이다. 폴더에 체크가 들어가면 **안의 파일도 체크된 것처럼**
보이기 때문이다.

이 시안은 **「폴더 하나 = 항목 하나」**를 택한다(결정 ②). 폴더를 체크하면 그 폴더가 *하나의
대상*이고, 삭제는 지금처럼 안의 내용까지 통째로 지운다. **자식 체크박스는 따라 켜지지 않는다.**

이유 셋:

1. 삭제 semantics가 이미 그렇다 — 폴더 삭제는 `remove_all`이다.
2. 3상태 전파는 §7의 "접힌 폴더 안은 선택에 넣지 않는다"와 정면으로 충돌한다.
3. 가상화(`show_rows`) 때문에 화면 밖 자식의 체크 상태를 계산하려면 렌더 전에 좌표·상태를
   다 계산하는 별도 패스가 필요하다.

대신 **말로 명시한다.** 체크된 폴더 행에 작은 표시("안의 내용까지")를 붙이고, 확인 문구가
그 사실을 분명히 말한다 — 위젯 모양으로 암시하는 대신 문장으로 약속한다.

### 5. 화면 — 0 / 1 / 다수

체크박스는 **좌측 고정 폭 열**로 자리를 잡는다(결정 ①). 꺼져 있을 때는 희미하게 두어 트리를
어지럽히지 않되 **있다는 사실은 보이게** 한다 — 사용자가 체크박스를 원한 이유가 수식키가 안
보이기 때문이므로, 체크박스마저 숨기면 같은 문제를 반복한다. 열을 항상 잡아 두면 선택 모드에
들어갈 때 목록이 옆으로 튀지 않는다. 폭 비용은 약 18px.

행 배경은 새로 만들지 않는다. 지금 파일 행은 hover만 `ui.visuals().widgets.hovered.weak_bg_fill`로
직접 칠하는데, 이걸 `designall::row_fill(tokens, checked, hovered)`로 갈아탄다 — 이 함수는 이미
`selected → selected_background`, `hovered → hover_background`를 돌려주고 워크스페이스 행이
쓰고 있다. cursor 행은 좌측 2px `tokens.accent` 레일이며 **체크와 별개**다 — 키보드 위치와
선택 여부는 다른 정보다.

선택 요약 줄은 **헤더 바로 아래, 스크롤 영역 위**에 둔다. 아래(에러/스피너/확인 문구 자리)에
두면 목록이 길 때 화면 밖으로 밀린다 — 삭제 확인이 정확히 그래서 안 보였다(2026-09-02).
요약 줄 왼쪽에는 **「보이는 행 전부」 체크박스**를 둔다(일부만 체크되면 중간 상태).

**0개 — 지금과 동일 (요약 줄 없음)**

### 6. 삭제 확인 — 섞인 체크를 어떻게 읽어주는가

`DeleteTarget`(2026-09-02)을 그대로 늘린다. **제스처 시점에 체크에서 만든 값 하나**를
확인 문구와 IO 요청이 함께 쓴다.

```rust
struct DeleteTargets {
    items: Vec<DeleteTarget>,   // path + label(루트 기준 상대경로) + is_dir
}
```

- 1개: 지금 문구 그대로(`file_tree.permanent_delete_prompt` / `..._folder_prompt`) — **회귀 없음**.
- 2개 이상: 개수와 종류를 말하고, **앞 5개 label을 그대로 나열**한 뒤 나머지는 개수로 접는다.
  이름을 하나도 안 보여주는 "3개를 삭제할까요?"는 2026-09-02에 고친 문제를 되돌리는 것이다.
  폴더 항목은 목록에서도 안의 내용까지 지운다고 다시 말한다.

새 i18n 키(5개 로케일 동시):

```
file_tree.checked_count          = {count} checked
file_tree.check_all_visible      = Check all visible
file_tree.checked_clear          = Clear
file_tree.trash_checked_prompt   = Move {count} items to the trash?
file_tree.trash_checked_mixed    = Move {files} files and {folders} folders (with everything inside) to the trash?
file_tree.checked_folder_note    = with everything inside
file_tree.checked_more           = …and {count} more
```

**다수 삭제 확인 (섞인 체크)**

```
┌────────────────────────────────────────────────┐
│ ⚠ 파일 2개와 폴더 1개를 (폴더 안의 내용까지)    │
│   휴지통으로 옮길까요?                          │
│     src/app.rs                                 │
│     src/mod.rs                                 │
│     tests/ — 안의 내용 전부                     │
│                                                │
│   [ 휴지통으로 이동 ]  [ 취소 ]                 │
└────────────────────────────────────────────────┘
```

**1개 삭제 확인 — 지금과 동일(휴지통 이동은 확인 없이, 실패했을 때만 이 문구)**

```
┌────────────────────────────────────────────────┐
│ ⚠ 휴지통으로 옮기지 못했습니다.                 │

│                                                │
│   [ 영구 삭제 ]  [ 취소 ]                       │
└────────────────────────────────────────────────┘
```

### 7. host 경계 — IO 큐가 1인 것을 어떻게 지키나

`FileTreeIoRequest`에 배치 변형 하나만 더한다. N번 큐잉이 아니라 **한 요청**이다.

```rust
Trash { targets: FileTreePathListPayload },   // 기존 단수 Trash를 대체
```

`FileTreePathListPayload`가 이미 항목 16개 / 256KB 상한과 NUL·길이 검증을 갖고 있어 새 검증
코드가 필요 없다. host(`app.rs`의 `Request::Trash`)는 지금 하는 `app_host_validate_tree` →
`trash::delete`를 **경로마다 반복**한다. 부분 실패는 "어디까지 됐는지"를 completion이 말해야
하므로 `TrashUnavailable`을 실패한 경로 목록과 함께 돌려주는 형태가 된다 — 여기가 이
시안에서 제일 큰 host 변경이고, 결정 ③의 상한을 16으로 두면 그만큼 작아진다.

### 8. 체크의 수명 — 새로고침·필터·이름변경·외부 변경

**한 줄 규칙: 화면에서 볼 수 없는 것은 체크에 남지 않는다.** 2026-09-02 수정이 세운
"보여준 것 = 지우는 것"과 같은 규칙이다.

- `rebuild_flat()` 뒤 `checked.retain(|p| flat_contains(p))` 한 번. `rebuild_flat`은 숨김
  토글·리스팅 반영·폴더 접기/펼치기가 모두 지나는 길목이라 여기 한 곳이면 된다.
- 결과: **폴더를 접으면 그 안의 체크가 풀린다.** 의도한 동작이다(접힌 폴더 안의 파일이
  삭제 목록에 몰래 남아 있는 것보다 낫다). **폴더 자신의 체크는 남는다** — §4에 따라 폴더는
  항목 하나이고, 접혀도 그 행은 화면에 있다. cursor도 같은 규칙으로 정리한다.
- 숨김 파일 필터를 끄면 `.`로 시작하는 행이 체크에서 빠진다(같은 규칙).
- **이름 변경**: 성공 completion을 적용하는 자리에서 옛 경로 → 새 경로로 **바꿔치기**한다.
  이름만 바꿨는데 체크가 풀리면 "이거 지워" 흐름이 끊긴다. 바꿔치기가 불가능하면 위 retain이
  정리한다.
- **외부 변경(워처 → `reload_dir`)**: 사라진 파일은 retain이 뺀다. 새로 생긴 파일은 **절대
  체크되지 않는다**.
- **삭제 성공 후**: 지워진 경로를 체크에서 뺀다. 이 정리가 없으면 다음 확인 문구가 이미
  없는 경로 이름을 말한다(2026-09-02 수정이 막은 실패 형태의 재발).
- **루트 전환/워크스페이스 전환**: `set_root`에서 전부 지운다.

### 9. 지금 단수 소비자들은 어떻게 되나

| 소비자 | 체크가 있을 때 |
|---|---|
| 더블클릭 열기 (문서 탭 / OS 기본 앱) | **그 행 하나만 — 지금 그대로.** 체크 16개를 탭 16개로 여는 사고를 만들지 않는다 |
| 드래그 소스 (payload `PathBuf`) | **잡은 행 하나 — 지금 그대로** (아래 「하지 않는 것」) |
| `MenuAction::CopyFile` → `copy_files_to_clipboard(&[path])` | 이미 리스트를 받는다. 체크를 그대로 넘기면 끝 (payload 상한 16이 그대로 적용) |
| `MenuAction::CopyPath` | 체크 전체를 개행으로 이어 붙여 복사 |
| `SidebarAction::InsertPath` (터미널 삽입) | 결정 ⑤ |
| `SidebarAction::CdPath` (cd) | 폴더 하나여야 의미가 있다. 체크가 2개 이상이면 메뉴 항목 **비활성** |
| `Rename` | 항상 1개. 체크가 2개 이상이면 비활성 |
| `⌘C` (`handle_copy_shortcut_signal`) | 체크가 있으면 **체크**, 없으면 지금처럼 포인터 밑 행 |
| `⌘V` (`PasteFromClipboard`) | **그대로** — 대상 폴더는 포인터 밑이지 체크가 아니다 |

### 10. 접근성

- egui 체크박스 위젯을 쓰면 접근성 트리에 `CheckBox` 역할과 체크 상태가 **저절로** 실린다.
  VoiceOver가 "src/mod.rs, 체크됨"으로 읽는다. 수식키 판은 라벨에 `selected` 상태를 손으로
  실어야 했고(관례를 잊으면 조용히 빠진다), 여기서는 위젯을 쓰는 것만으로 지켜진다.
- 테스트도 같은 이유로 튼튼하다 — Relay 설정이 이미 쓰는
  `get_by_role_and_label(egui::accesskit::Role::CheckBox, ..)`로 kittest가 행을 직접 집는다.
- 한계는 남는다: egui/accesskit에 live region이 없어 **"3 checked"가 바뀔 때 자동으로 읽히지
  않는다.** 이 한계를 문서에 남기고, 대신 체크박스마다 상태가 실려 커서를 옮길 때 낱개로
  확인되게 한다.
- 삭제 확인이 열릴 때 버튼에 `request_focus()`를 줄지는 결정 ⑥.
- 키보드 전용 사용자에게 필요한 최소 경로: Tab으로 트리 진입 → ↑↓로 이동 → Space로 체크 →
  요약 줄의 [Trash] 버튼. **⇧F10(컨텍스트 메뉴 키) 지원은 이 시안 범위 밖**이며, 그때까지
  요약 줄 버튼이 키보드 경로다(그래서 요약 줄에 버튼을 둔다).

## 하지 않는 것 (일부러 안 가져가는 대가)

- **폴더 3상태 전파.** §4. 접힌 폴더 안을 체크에 넣지 않는다는 §8 규칙과 정면 충돌하고,
  가상화 때문에 화면 밖 자식 상태를 계산할 수 없다.
- **다중 드래그&드롭.** payload가 `PathBuf` 하나이고 `file_drop::row_drop_target`의 순환
  검사(`dragged`)도 단수 전제다. `Vec<PathBuf>`로 바꾸면 드롭 판정·삽입선·순환 검사가 전부
  다시 설계된다. v1에서는 드래그는 **한 개만** — 체크가 여러 개여도 드래그는 잡은 행이다.
- **마퀴(고무줄) 선택.** 행은 `show_rows` 가상화라 화면 밖 행에 rect가 없다. 체크박스가
  있으면 이 제스처의 필요 자체가 줄어든다.
- **Delete/⌫ 키 바인딩.** 트리에 포커스가 있는 줄 모르고 누르는 것이 2026-09-02 수정이
  다룬 사고와 정확히 같은 종류다. 버튼과 메뉴만으로 시작한다.
- **접힌 폴더 안까지 ⌘A.** 보이는 행만 고른다.
- **체크의 영속화.** 앱 재시작·워크스페이스 전환에 체크는 남지 않는다.
- **워크스페이스/세션 목록의 다중 선택.** 이 시안은 **파일 트리만** 다룬다. 두 목록은
  독립 도메인이다.
- **트리 전체의 키보드 우선순위 변경.** 터미널이 여전히 기본 키보드 소유자다.

## 결정이 필요한 것

**① 체크박스를 언제 보여줄까** — 체크박스 방향에서 새로 생긴 결정.
사이드바 트리는 좁다.
- **(A) 열을 항상 잡고, 꺼져 있을 땐 희미하게 — 권장.** 있다는 사실이 보이고(=발견 가능),
  선택 모드 진입 시 목록이 옆으로 튀지 않는다. 폭 비용 약 18px.
- (B) hover한 행에만 나타난다. 가장 조용하지만, 수식키가 안 보여서 겪은 문제를 반복한다.
- (C) 「선택 모드」 토글을 켰을 때만. 가장 깔끔하지만 조작이 한 단계 늘고 상태를 하나 더
  관리해야 한다.

**② 폴더 체크의 의미** — 체크박스 방향에서 새로 생긴 결정.
- **(A) 폴더 하나 = 항목 하나 — 권장.** §4의 이유 셋. 확인 문구가 "안의 내용까지"를 명시한다.
- (B) 3상태 전파(자식까지 체크). 가장 익숙하지만, 접힌 폴더 안을 계산할 수 없어 "보이는 것만
  선택"이라는 안전 규칙이 무너진다.

**③ 선택 상한** — 수식키 판에서 이월.
`FILE_TREE_PATH_LIST_MAX_ITEMS = 16`을 그대로 쓸까(넘으면 기존 `PathListTooLarge`로 거절),
아니면 올릴까? 16이면 host·payload 변경이 사실상 없다. 올리면 배치 trash의 부분 실패 처리가
커진다. **체크박스는 ⌘A가 쉬워서 16을 더 자주 넘길 수 있다는 점**은 감안해야 한다. 시안은
16 유지를 권한다.

**④ 확인 문턱** — 수식키 판에서 이월.
지금 휴지통 이동은 **확인 없이** 실행되고 실패했을 때만 영구삭제 확인이 뜬다. 체크가 여러
개면 (a) 2개 이상일 때만 확인, (b) 1개도 확인, (c) 지금처럼 확인 없음 — 어느 것인가?
시안은 (a)를 권한다(1개는 지금 동작 그대로 = 회귀 없음).

**⑤ 다중 체크일 때 「터미널에 경로 삽입」** — 수식키 판에서 이월.
체크 전체를 공백으로 이어 넣을까(명령 인자로 바로 쓰인다), 우클릭한 행 하나만 넣을까
(더블클릭·드래그와 같은 규칙이라 "행 제스처는 항상 그 행"으로 일관된다)?

**⑥ 삭제 확인이 뜰 때 포커스를 가져올까?** — 수식키 판에서 이월.
스크린리더에는 필요하고(안 가져오면 확인이 뜬 사실을 모른다), 터미널에 타이핑 중인
사용자에게는 방해다.
