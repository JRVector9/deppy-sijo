# i18n 키 누락 재발 방지 — `i18n-check` key-coverage 게이트 (2026-08-19)

## 증상

터미널 상단에 빨간 배너로 **`runtime.spawn_failed.invalid_command`**라는 키 문자열
자체가 그대로 노출됐다(사용자 보고).

## 확정한 원인

- `crates/runtime/src/in_process.rs`가 `MessagePayload::new("runtime.spawn_failed.invalid_command")`로
  `SpawnFailed` 이벤트를 올린다.
- `crates/app/src/ui/workspace.rs`가 `crate::ui::render_message(catalog, message)` →
  `catalog.t(&message.message_id, &args)`로 그 키를 문구로 바꾼다.
- `Catalog::t`는 primary/fallback 로케일 둘 다에 키가 없으면 **키 문자열 자체를
  그대로 반환**한다(`crates/i18n/src/lib.rs`의 `.unwrap_or(key)`).
- 그 키가 **5개 로케일(en-US/ko-KR/ja-JP/zh-Hans/zh-Hant) 어디에도 없었다.**
- 기존 `cargo run -p xtask -- i18n-check`는 `cargo test -p i18n`의
  `required_locales_have_complete_keys`/`all_bundled_locales_match_fallback_order_and_placeholders`에
  의존하는데, 이 테스트들은 **로케일 "간" 키 짝맞춤**만 본다 — fallback(en-US)
  기준으로 다른 로케일에 키가 더 있거나 없으면 잡지만, **5개 로케일 모두에 똑같이
  없는 키**는 "일치"로 보고 통과시킨다. 코드가 실제로 어떤 키를 참조하는지는
  전혀 보지 않는다.

전수 조사 결과 같은 부류(코드가 참조하지만 로케일 파일에 없는 키)가 두 개 더
있었다: `runtime.spawn_failed.session_limit`, `runtime.spawn_failed.shell_secret`.
셋 다 `crates/runtime/src/in_process.rs`의 `Worker` 메서드들이 참조하는
정적 문자열 리터럴이었다.

## 대응 1 — 누락 키를 채운다

5개 로케일 `crates/i18n/locales/*/messages.txt`의 `runtime.spawn_failed.*` 그룹에
세 키를 추가했다(다른 `runtime.spawn_failed.*`와 같은 위치·순서로 — `cargo test -p i18n`이
로케일 간 키 **순서**까지 비교하기 때문에 5개 파일 모두 같은 자리에 넣어야 한다).

| 키 | 발생 조건 |
|---|---|
| `runtime.spawn_failed.invalid_command` | 구조적으로 잘못된 `RuntimeCommand`가 worker에 들어옴 |
| `runtime.spawn_failed.session_limit` | `RUNTIME_SESSION_CAP` 초과로 세션을 못 띄움 |
| `runtime.spawn_failed.shell_secret` | 셸 spawn 전 secret 환경변수 해석 실패 |

세 키 모두 인자(`{error}` 등)를 넘기지 않는 호출부라 정적 문구로 작성했고,
기존 `runtime.spawn_failed.suspended`(대시 연결/이유+미시작 절 구조)와 같은
어투를 따랐다.

## 대응 2 — 근본 대책: `i18n-check`가 "코드 참조 키 ⊆ 로케일 키"를 직접 검사

`xtask/src/main.rs`에 `check_i18n_key_coverage()`를 추가하고 `i18n_check()`에서
호출한다. `crates/` 전체를 스캔해 아래 두 호출부의 **문자열 리터럴** 키 인자를
추출하고, 5개 로케일 전부에 있는지 대조한다.

- `catalog.t("KEY", ...)` (그리고 `catalog` 대신 `text`/`i18n`/`cat` 등 다른 변수명이어도
  잡는다 — `.t("` 패턴 자체로 찾는다. `MessagePayload`를 렌더하는
  `crate::ui::render_message`도 내부적으로 `catalog.t(&message.message_id, ...)`를
  호출하므로 별도 패턴이 필요 없다.)
- `MessagePayload::new("KEY")` (`runtime::MessagePayload::new(...)` 형태도 포함 —
  경로 유무와 무관하게 `MessagePayload::new(` 부분 문자열로 찾는다.)

### 추출 방법

파일마다 `syn::parse_file`로 파싱한 뒤, 최상위 아이템 단위로 토큰 스트림을
공백 제거한 "컴팩트" 문자열로 바꿔 그 안에서 `.t("`/`MessagePayload::new("` 바로
뒤의 문자열 리터럴을 찾는다. 이 방식은 이미 `check_boundary`의
`check_leaf_semantic_boundary`/`check_app_composition_source`가 쓰는 것과 동일한
패턴이다 — 새 관례를 만들지 않고 기존 관례를 재사용했다. 공백을 지운 토큰
스트림을 쓰기 때문에 `catalog.t(\n    "key",\n    &[],\n)`처럼 여러 줄에 걸친
호출도 한 줄로 뭉쳐져 그대로 잡힌다.

### 테스트 코드 오탐 방지

각 최상위 아이템에 `#[cfg(test)]`가 붙어 있으면(개별 헬퍼든, 파일 끝의 통짜
`mod tests { ... }`든) 통째로 스캔에서 제외한다(`top_level_item_is_test_only`,
`check_boundary`가 이미 쓰는 판정 함수를 그대로 재사용). 이 저장소는 테스트를
전부 `#[cfg(test)]` 아이템(주로 파일 끝 `mod tests`)에 모아두는 관례를 지키므로
안전하다. 이 제외가 없으면 예를 들어 `crates/app/src/app.rs`의
`overflow_spawn_replay` 테스트 헬퍼가 쓰는 `MessagePayload::new(format!("agent.failed.{idx}"))`나
`crates/app/src/ui/workspace.rs`의 `MessagePayload::new("shell.failed")`(둘 다
존재하지 않는 걸 알면서 이벤트 replay/dedup 로직만 검증하려고 일부러 쓰는 가짜
키) 같은 경우가 오탐을 낸다.

### 정적으로 못 잡는 범위 (정직한 문서화)

`.t(`/`MessagePayload::new(` 바로 뒤가 문자열 리터럴이 아니면(변수, `format!()`,
`xxx_key()` 헬퍼 함수 호출, match 팔에서 고른 상수 등) 컴파일타임에 값을 알 수
없어 정적으로 못 잡는다. 이런 호출은 "dynamic"으로 개수만 세고 통과시킨다 —
잡을 수 있는 척하지 않는다.

이 저장소를 대상으로 실측한 결과(2026-08-19 기준, `cargo run -p xtask -- i18n-check`
출력에 매번 정확한 수치가 찍힌다):

- 전체 호출부 1,067건 중 **리터럴 1,006건**(94%)은 이 게이트가 직접 검증한다.
- **동적 61건**(6%)은 못 잡는다. 전부 아래 패턴 중 하나다.
  - enum/구조체에 붙은 `xxx_key()`/`message_key()`/`title_key()`/`hint_key()`/
    `close_key()`/`effort_message_key()` 같은 헬퍼가 반환하는 키
    (`crates/app/src/ui/agent_launcher.rs`, `settings.rs`, `agent_sessions.rs`,
    `work_history.rs`, `workspace.rs`, `notifications.rs`, `fleet.rs`,
    `diff_panel.rs`/`diff_viewer.rs`/`git_panel.rs` 등)
  - 함수 인자로 받은 `key`/`message_id`를 그대로 넘기는 경우
    (`crates/app/src/ui/mod.rs::render_message`, `notifications.rs`의
    `NotificationItem.message_id`)
  - `crates/runtime/src/in_process.rs:577`처럼 함수 파라미터 `message_id`를 그대로
    `MessagePayload::new(message_id)`에 넘기는 경우

이런 헬퍼 함수 자체(예: `fn effort_message_key(effort: Effort) -> &'static str`)는
보통 내부적으로 `match`로 리터럴을 고르는데, 그 리터럴들은 **함수 정의부**에서는
`.t("...")` 형태가 아니라 단순 `&'static str` 반환값이라 이 게이트의 두 패턴
어디에도 걸리지 않는다. 즉 이런 헬퍼가 반환하는 키 자체가 로케일에 있는지는
**이 게이트가 전혀 커버하지 못한다** — 별도로 그 헬퍼들이 반환 가능한 모든
리터럴을 열거해 검사하는 확장이 필요하다면 후속 작업으로 남긴다.

### 오탐 방지 확인

- `crates/i18n/src/lib.rs`의 `catalog.t("missing.key", &[])`(폴백 동작을 일부러
  검증하는 테스트)는 `#[cfg(test)] mod tests` 안에 있어 제외된다.
- `crates/app/src/app.rs`/`crates/app/src/ui/workspace.rs`의 replay/dedup 테스트가
  쓰는 가짜 키(`"shell.failed"`, `format!("agent.failed.{idx}")`,
  `format!("spawn.failed.{idx}")`)도 전부 파일 끝 `#[cfg(test)] mod tests` 안이라
  제외된다.

## 검증 — 게이트가 실제로 실패하는지 증명

`crates/i18n/src/lib.rs`(소유 영역 안)에 존재하지 않는 키를 참조하는 프로덕션
함수를 임시로 추가했다:

```rust
#[allow(dead_code)]
fn __i18n_check_guard_smoke_test(catalog: &Catalog) -> String {
    catalog.t("zzz.definitely.not.a.real.key.for.smoke.test", &[])
}
```

`cargo run -p xtask -- i18n-check` 실행 결과:

```
VIOLATION: crates/i18n/src/lib.rs: key 'zzz.definitely.not.a.real.key.for.smoke.test' missing from locale(s): en-US, ja-JP, ko-KR, zh-Hans, zh-Hant
Error: i18n key coverage 실패: 1건
```
(exit code 1)

임시 함수를 되돌린 뒤 다시 실행하면:

```
i18n key coverage OK — 리터럴 키 호출 1006건을 로케일 5개와 대조; 정적으로 못 잡는 동적 키 호출 61건(...)
i18n-check OK
```
(exit code 0, `git diff`로 원상복구 확인)

## 남은 한계 요약

- 동적으로 조립되는 키(변수/함수 반환값/`format!()`)는 이 게이트가 못 잡는다 —
  위 "정적으로 못 잡는 범위" 절 참고.
- 로케일 파일 자체의 포맷(`key = value`)이 바뀌면 `locale_key_set`이 조용히 빈
  집합을 만들 수 있다 — 다만 `cargo test -p i18n`의 `parse_locale_file`이 같은
  포맷을 먼저 파싱하므로 포맷 붕괴는 그쪽에서 먼저 드러난다.
- 이 게이트는 "코드가 쓰는 키가 로케일에 있는지"만 본다. "로케일에 있는데 코드가
  안 쓰는 키"(죽은 번역)는 범위 밖이다 — 별도 관심사라 이번 작업에서는 다루지
  않았다.
