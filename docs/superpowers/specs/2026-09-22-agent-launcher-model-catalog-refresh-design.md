# 에이전트 런처 모델 카탈로그 자동 갱신 설계

## 목표와 승인 범위

사용자가 승인한 방식은 **런처를 열 때 비동기 갱신**이다. Grok 4.7처럼 CLI에 추가된
모델을 앱 재시작·수동 새로고침 없이 다음 런처 열기에 반영한다. 새 버전이 생겼다는
이유로 사용자의 기본 모델을 바꾸지 않는다. 상시 watcher·주기 polling은 추가하지 않는다.

현재 Grok object/info 파서는 새 모델 ID를 이미 읽는다. 원인은 snapshot이 있으면 런처를
다시 열어도 감지 worker를 요청하지 않는 수명주기에 있다. 아래 여섯 보완 계약을 함께
적용해야 자동 갱신을 안전하게 활성화할 수 있다.

## 제공자별 지원 범위

| 제공자 | 목록 소스 | 자동 반영의 의미 |
| --- | --- | --- |
| Grok | `.grok/models_cache.json` | CLI가 캐시에 반영한 모델·강도 |
| Codex | `.codex/models_cache.json` | CLI가 캐시에 반영한 공개 선택 가능 모델 |
| Kimi | `.kimi-code/config.toml` | 등록한 모델·thinking 설정 변경 |
| Qwen Code | `.qwen/settings.json` | 등록한 modelProviders 변경 |
| Cursor | 설치된 CLI의 `--list-models` | CLI가 현재 계정에 제시하는 모델; 별도 worker |
| Claude | CLI SDK 초기화의 지원 모델 응답 | 실제 응답 계약을 검증한 버전에서 동적 항목 사용 |
| 나머지 CLI | 기존 설치 감지 | 모델 자동 발견 지원으로 확대하지 않음 |

Grok·Codex의 캐시가 아직 서버의 새 목록을 받지 않았다면 앱도 먼저 발견할 수 없다.
Kimi·Qwen은 원격 전체 목록이 아니다. 앱은 직접 모델 API나 인증 토큰을 읽지 않는다.

## 보완 1 — Cursor 목록과 실행을 함께 지원

`supports_model`, 동적 모델 목록, 선택 상태, `build_launch_spec`의 `--model` 검증을
하나의 PR로 연결한다. 목록만 보이면서 실행은 거절되는 중간 상태를 배포하지 않는다.
`--list-models`와 `--model`은 [공식 CLI 문서](https://cursor.com/docs/cli/reference/parameters)에
명시돼 있다. 목록의 JSON 출력은 확인되지 않았으므로 `--output-format json`을 가정하지
않는다. 실제 CLI 출력에서 모델 ID·라벨을 확인한 fixture를 사용한다. 추론 강도를
모델 이름으로 추측하지 않으며 확인되지 않은 capability는 제시하지 않는다.

CLI 조회는 파일 감지 worker와 분리한다. 제공자당 pending 1건, 결과 1건, 실행 10초,
stdout/stderr 각각 256KiB, 모델 최대 64개, ID 256바이트/라벨 128바이트로 제한한다.
timeout·출력 초과·취소 시 소유한 프로세스와 파이프를 종료·회수한다. PATH의 감지된
실행 파일을 직접 실행하고 셸 문자열을 만들지 않는다. 조회용 디렉터리는 프로젝트
밖에 두고 대화 프롬프트·세션 생성·trust 우회 옵션은 사용하지 않는다.

## 보완 2 — Claude 별칭과 동적 발견을 구분

[공식 모델 설정 문서](https://code.claude.com/docs/en/model-config)의 별칭 해석은 CLI에
맡긴다. opus 같은 별칭이 새 버전을 실행하는 것과 런처에 새 모델군이 추가되는 것은
별개다. [공식 SDK](https://github.com/anthropics/claude-agent-sdk-typescript)의 초기화/지원
모델 계약을 설치 CLI와 대조하고, 프롬프트 없이 받은 모델 ID·표시명·지원 강도만 채택한다.
SDK 문서의 존재만으로 설치 CLI에서 검증됐다고 기록하지 않는다.

격리된 디렉터리에서 프로젝트 설정·MCP·hooks·세션 저장을 비활성화한 초기화만 허용한다.
CLI가 그 격리 계약을 지원하지 않으면 probe를 실행하지 않는다. Cursor와 같은 실행/출력
상한을 적용한다. 지원 응답이 없거나 검증에 실패하면 기존 별칭·사용자 설정 모델을
유지한다. Anthropic API 목록으로 CLI 구독 가용 모델을 대신 추정하지 않는다.

## 보완 3 — 갱신 때문에 목록 위치가 움직이지 않음

기존 snapshot을 그대로 표시하며 로딩 표시를 고정 높이 24pt 헤더 안에 둔다. 탐지 중에만
생기는 별도 spinner 행은 없앤다. 설치 목록 ScrollArea ID와 카드/모델 항목 ID는
제공자·모델 ID에 고정한다. 모델·강도 popup 또는 pointer 조작 중에는 새 snapshot 적용을
미루고, 종료 후 한 번 적용한다. 대기 snapshot은 최신 1개만 보관하며 launch_pending 중에도
교체하지 않는다. 완료 결과가 동일하면 불필요한 교체/표시정보 재생성을 하지 않는다.

실제 설치/모델 목록 변화 자체에 따른 필요한 내용 변경과 갱신 표시의 레이아웃 이동은
구분한다. 화면의 깜빡임 없음은 테스트만으로 PASS 처리하지 않고 승인된 재빌드 후 확인한다.

## 보완 4 — 읽기 실패와 정상 빈 목록을 구분

카탈로그 결과는 `Ready(Vec<ModelChoice>)`, `Missing`, `Unavailable`, `Unsupported`로
구분한다. `Ready([])`는 정상적인 빈 목록이며 예전 목록/내장 모델을 되살리지 않는다.
잘못된 JSON/TOML·루트 스키마 오류는 Unavailable, 파일 삭제는 Missing이다. 개별 잘못된
항목은 기존 관대한 파서대로 건너뛰고 유효 항목을 유지한다. 설정만 있는 Kimi/Qwen은
모델 미등록을 정상 빈 목록으로 처리한다. Codex/Grok 카탈로그는 models 필드를 요구한다.

최초 Unavailable/Missing에는 기존 내장 폴백을 쓴다. 갱신 Unavailable은 **동일 설치·계정
범위를 확인할 수 있을 때만** 마지막 정상 목록을 유지한다. 정상 빈 목록·소스 삭제·실행 파일
교체·로그아웃/계정 변경은 이전 목록을 폐기한다. 인증 범위를 증명할 수 없으면 보존하지 않는다.
계정 범위 확인은 제공자의 비밀이 아닌 identity 또는 인증 파일의 변경 메타데이터로 제한하며
비밀 본문은 저장/로그하지 않는다. 계정 소스를 확정하지 못한 제공자에는 보존을 활성화하지 않는다.

보존은 snapshot 내 제공자별 1벌, 최대 64개 모델, 성공 후 10분 이내로 제한한다. 시간 초과 시
추가 timer 없이 다음 열기/갱신에서 폐기한다. 실패 때 성공 시각을 갱신하지 않는다. worker의
30초 idle 종료와 무관하게 App snapshot이 수명을 소유한다. 파일 읽기는 사전 metadata 확인과
`Read::take(8MiB + 1)`로 읽는 도중 파일이 커져도 할당량을 제한한다.

## 보완 5 — 자동 기본값과 사용자 선택 분리

모델과 강도 각각 명시 선택 여부를 저장한다. 런처 재열기·제공자 전환에는 둘 다 자동 상태로
초기화한다. 새 snapshot이 도착하면 미조작 모델/강도는 새 CLI 기본값을 따른다. 사용자가 고른
유효 모델/강도는 유지한다. 사용자가 모델을 바꾸면 새 모델의 기본 강도로 초기화하며, 이후
직접 고른 강도만 고정한다. 지원에서 사라진 선택은 새 기본값으로 돌아가고 명시 선택도 해제한다.
YOLO·워크스페이스·실행 의도는 모델 갱신으로 초기화하지 않는다.

설치 Claude의 실제 initialize 응답에는 supportedEffortLevels가 있지만 기본 강도는 없었다.
따라서 동적 모델에 확인된 사용자 강도 설정도 없으면 Low를 임의 지정하지 않고
‘CLI 기본값’을 표시하고 --effort를 생략한다. 사용자가 직접 지정한 강도와 명시적으로
선택한 CLI 기본값은 각각 보존한다. 5개 로케일에 동일한 항목을 제공한다.

## 보완 6 — 모든 열기 경로의 공통 갱신 요청

`AgentLauncherUi::open_for`가 1회성 갱신 요청을 기록하고 App이 소비한다. `open_for_kind`는
이를 호출하므로 사용자 열기·최초 자동 제안·작업 이력 NewRun에 같은 계약이 적용된다.
실패하여 열리지 않은 NewRun은 요청하지 않는다. 재열기 요청은 현재 in-flight 작업 뒤 최대
1번 후속 갱신으로 합친다. 이미 닫혔더라도 완료 결과는 다음 열기의 snapshot으로 쓸 수 있다.
수동 Refresh는 같은 bounded worker 경로를 사용한다. 제출 Full이면 요청을 보존한다.

## 개발 순서와 검증 경계

실행 계획: [PR 단위 개발 계획](../plans/2026-09-22-agent-launcher-model-catalog-refresh.md).
PR-MC1 입력 결과 구분/읽기 상한 → PR-MC2 안전 병합·모든 열기·기본값·안정된 갱신 UI →
PR-MC3 Cursor → PR-MC4 Claude 순서다. 실제 GitHub PR 번호가 아닌 작업 단위 ID다.
자동 갱신은 PR-MC2의 보호 계약을 갖춘 뒤 활성화한다.

화면 밖 파서·병합·선택·프로세스 수명은 집중 실패 테스트 후 수정한다. UI는 별도 승인된
재빌드·재실행 후 직접 확인한다. 테스트 실행 파일 컴파일과 배포 앱 재빌드를 구분한다.
이번 요청은 개발 착수이며 release 재빌드·재실행·merge·force-push를 수행하지 않는다.

## 2026-09-22 구현과 실제 검증

MC1~4 소스 연결을 완료했다. 디스크 카탈로그는 기존 worker, Cursor/Claude는 제공자별
lazy worker 하나씩이며 각각 요청/결과 1건만 유지한다. 설치 감지에도 요청 세대를 연결하여
이전 감지가 새 열기의 외부 조회 요청을 소비하지 못하게 한다. 외부 조회의 이전 세대 결과와
실행 파일 metadata revision이 다른 결과를 버린다. 외부 조회 완료까지 고정 헤더의 로딩
표시를 유지하며 worker 실패도 조회 실패로 정리한다. 외부 인증 범위를 독립적으로 확인할 수
없어 실제 조회 실패 시 과거 모델은 폐기하고 기존 폴백을 사용한다. 디스크 감지 완료만으로
아직 조회 중인 외부 목록을 내장 목록으로 바꾸지 않는다.

프로세스 조회는 Unix에서 비차단 파이프와 소유한 process group으로 구현했다. Windows는
외부 조회를 실행하지 않고 기존 폴백을 사용한다. macOS의 실제 설치 CLI로 Cursor 64개
(상한 적용), Claude 5개 모델 조회를 확인했다. Claude는 safe-mode, 빈 tools/MCP,
disableAllHooks, no-session-persistence와 initialize control request만 사용하며 사용자
프롬프트를 보내지 않는다. 지원 옵션이 없는 CLI는 조회를 진행하지 않는다.

로직 검증 결과와 정확한 로그는 개발계획/인계 문서에 기록한다. 실제 앱 화면의 깜빡임,
재빌드·재실행 확인은 사용자의 별도 요청 때 수행하며 아직 완료로 기록하지 않는다.
